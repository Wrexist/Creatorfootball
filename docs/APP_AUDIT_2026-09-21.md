> Historical audit. For the 22 September completion status, see [the closure matrix](AUDIT_CLOSURE_2026-09-22.md) and [current implementation report](REDESIGN_REPORT.md). Findings below retain their original evidence; they are not the current open-work list.

**Reviewed 21 September 2026. Baseline commit: `868c7b21c5e50ae1a2269d1e53b5c4d496e6c615`.**

The app has a substantial playable foundation, but it is not release-ready. The largest problems are lost or inconsistent career state and systems that have working screens and isolated engine functions without a complete connection between them. Redesign should follow the career-safety fixes so the new interface communicates behavior the game actually supports.

This review produced **36 implementation work items**, an actual-screen gallery, source evidence, and local verification results. Product code was not changed.

## What was checked

Repository-wide architecture and security-sensitive searches; independent security and architecture reviews; focused reads of persistence, lifecycle, matches, transfers, economy, training, facilities, progression, social systems, native packaging, CI and tooling; every main management route in a real Chromium browser against the production build; creation, player/creator details, live match, match sheets, results, negotiations, store and deletion dialogs; and desktop comparisons.

The gallery contains **39 distinct captured URLs** and **85 screenshots** including page bottoms and dialogs. Phone captures are **393 × 852**; desktop captures are **1440 × 1000**. Screens show an isolated generated career, not an existing user's save. A match was played through to results and the next week in that context. Destructive confirmation was photographed and cancelled.

This is a broad app review, **not an exhaustive line-by-line security certification**. The supporting artifacts distinguish fully reviewed files from targeted reads and unreviewed files. No real iPhone/Android device, macOS archive, production headers, signing configuration, ignored secrets, or external infrastructure was audited. Browser screenshots do not prove every interaction, state, or accessibility behavior. Production source was kept unchanged.

## Security assessment

**No exploitable remote or cross-user vulnerability was confirmed in the reviewed first-party paths.** The game currently runs locally, loads bundled fictional content, has no account/backend/shared economy, and does not implement checkout. Local save editing is not an authorization bypass in this architecture. The noncryptographic checksum detects some corruption; it does not authenticate saves.

**Dependency audit: 15 advisory entries — 10 high, 5 moderate, 0 critical.** These are package audit classifications, not 15 demonstrated exploitable game vulnerabilities. One advisory is represented for both Vitest and its mocker package. The observed paths are primarily build/development tooling. Review the actual lockfile and dependency parents rather than blindly upgrading declared lower bounds.

| Package / path | Assessment and action |
|---|---|
| `@xmldom/xmldom` through Capacitor CLI → plist | Multiple parsing/serialization/resource-exhaustion advisories; audit suggests patched `0.9.12`. Update through a compatible parent or reviewed override and rerun native sync/build validation. No remote app XML input was found. See [maintainer advisory](https://github.com/xmldom/xmldom/security/advisories/GHSA-965w-775f-mr7g). |
| `js-yaml` through ESLint configuration tooling | CPU-exhaustion advisory; patched `4.3.2`. Update and rerun lint. No game runtime YAML input was found. See [maintainer advisory](https://github.com/nodeca/js-yaml/security/advisories/GHSA-2883-xcg3-v3hh). |
| Vitest / `@vitest/mocker` | Path traversal advisory; patched Vitest `4.1.11`. Exploitation depends on a reachable relevant mock/dev-server endpoint. Current scripts run Node tests and do not establish the vulnerable public plugin exposure. Plan the major-version migration and keep test servers private. See [maintainer advisory](https://github.com/vitest-dev/vitest/security/advisories/GHSA-82fw-gwwq-j7x9). |
| `uuid` | Buffer bounds advisory for selected APIs when a buffer is provided; audit suggests `>=11.1.1`. Trace the CLI dependency path and upgrade compatibly. No first-party game call to the affected API was established. See [advisory](https://github.com/advisories/GHSA-w5hq-g745-h8pq). |

Defense-in-depth work: make LAN dev serving opt-in (`vite.config.ts:44`), explicitly limit CI permissions, pin third-party actions to reviewed SHAs, monitor advisories, and configure/test an appropriate production CSP when the actual host is selected. These are hardening items, not proof of an existing exploit. Before adding save imports, community packs, online purchases or cloud saves, review the new trust boundaries: unknown-safe schemas and size limits, provenance, server/platform entitlement verification, ownership and conflict handling. Do not rely on client checksums for future paid entitlements.

## Prioritized implementation backlog

**P1:** fix before release. **P2:** complete the promised core experience. **P3:** polish and measured release qualification. Priorities describe product impact, not CVSS severity. “Runtime” means reproduced in an isolated local context; “source” means traced through current code with prerequisites stated.

### A. Career safety and release blockers

| ID | Priority / evidence | Problem and implementation | Acceptance gate |
|---|---|---|---|
| 01 | P1 · runtime | **Existing saves disappear when writes fail.** `platform/storage.ts:21-46` performs a write probe before reads, switches permanently to an empty memory Map and later reports volatile writes as successful. Separate readable storage from writable storage, retain accessible saves, expose persistent durability status, and make retry/export possible. Deletion must still remove the durable original after fallback. | Existing career loads at full quota; storage-disabled mode is clearly labelled; reload never silently loses progress reported as durable; abandoned careers cannot reappear. |
| 02 | P1 · runtime/source | **Save failures bypass notifications; manual save reports success early.** `persistence/save.ts:159-177`, `gameStore.ts:64-78,195`, `SettingsScreen.tsx:119`. Normalize exceptions into a typed persistence result, await manual saves, distinguish durable/volatile/failed, and keep an unsaved indicator until recovery. | Inject failure at backup, primary and metadata writes; no unhandled rejection or false “Saved”; advanced in-memory state and retry semantics are explicit. |
| 03 | P1 · runtime | **Recovery can skip a valid backup.** `save.ts:104-128,181-228` assumes nested JSON types and returns early for missing primary. Validate unknown input without throwing and inspect backup for both absent and corrupt primaries. Recovery copy must reflect what was actually checked. | Malformed club arrays, missing primary, invalid JSON, bad checksum and newer versions receive correct recovery outcomes without deleting usable data. |
| 04 | P1 · runtime | **Recovered backup can be overwritten by the corrupt primary.** `save.ts:159-163,226`. Promote only verified primary generations and preserve the good backup until new primary is durable; prefer a transaction or staged generation commit. | Crash/failure between every write leaves at least one verified recoverable generation. |
| 05 | P1 · source | **Overlapping saves and stale async work can overwrite current state.** `gameStore.ts:139-207`. Serialize mutations/persistence, bind writes to save identity/revision and invalidate pending operations on career deletion or replacement. | Rapid settings/action changes, advancing then abandoning, and starting a new career cannot resurrect or overwrite old state. Add multi-tab ownership/conflict handling for web. |
| 06 | P1 · source | **Second career can inherit old match commits.** `MatchResultScreen.tsx:44,70,80` uses a module-global Set; new games reuse season/fixture IDs. Move idempotency into a persisted save/fixture transaction and record acceptance only after successful application. | Same club, two careers, same app session: opening result advances both correctly; double mounts/retries commit once. |
| 07 | P1 · runtime | **Old or unrelated match results can be applied to the current fixture.** `gameStore.ts:170-181`, `game/cycle.ts:108-126`, `applyResult.ts:76-81`. Validate scheduled status, player participation, season/week, teams and exact fixture/match identity at both route and engine boundaries. | Old/future/opponent-only live links are rejected or show historical reports; mismatched results cannot advance the player fixture. |
| 08 | P1 · source | **Match completion/report is not durable before navigation.** `MatchLiveScreen.tsx:208-209`, `MatchResultScreen.tsx:69-82,140`. Persist a pending completion/result transaction before the transition; reconstruct reports from saved results and handle reload/back/background coherently. | Force-close at full time and each result stage; reopen to the correct committed or resumable match; no false claim that consequences were applied. |
| 09 | P1 · source | **Bought players retain old contracts and can later be released.** `market/engine.ts:326-339`, `game/mutations.ts:79-82`, `cycle.ts:499-532`. Retire the old contract atomically; expiry must check current contract and club identity. | Buy a player whose old contract expires next week; advance and reload; new contract and ownership remain intact with one active contract. |
| 10 | P1 · source | **Academy transfers can leave duplicate ownership and break saving.** `transfers/negotiation.ts:653-655`, market search and season intake paths. Remove from both seller squads and stale lineup references through one registration helper. | Buy a generated academy prospect, advance, save and reload; exactly one club owns the player and all squad/contract references agree. |
| 11 | P1 · source/runtime | **Player training is not executed.** `training/training.ts:85` has no production caller; `worldTick.ts:391-394` excludes the player club from development. Add one authoritative training stage to `advanceCycle`; merge development, injuries, results, cohesion and events. | Change programme/intensity/focus in UI, advance a week, see actual results and expected development. Verify training/medical facility modifiers without double development. |
| 12 | P1 · runtime/source | **Social cash rewards are discarded.** Social campaigns/milestones return their own ledger snapshots, then `cycle.ts:398` overwrites them with the older ledger. Share one transaction owner or adopt the returned ledger before later work. | Milestone and sponsored-campaign status, reward display, cash transaction and idempotency all persist together; retry does not lose or duplicate payment. |
| 13 | P1 · source | **Four match settings do not control matches.** `SettingsScreen.tsx:132-166` persists settings but match store uses separate defaults. Wire speed, presentation, commentary and auto-decision timeout. A broadcast option must actually replace expensive pitch rendering, or be renamed to describe the real behavior. | Each setting changes the next/live match as documented and survives restart; disabled auto-resolve really waits; commentary can be hidden. |
| 14 | P1 · source | **Committed iOS dependency paths are invalid Windows-style Swift literals.** `ios/App/CapApp-SPM/Package.swift:15-17`. Regenerate managed package inputs on macOS and verify portable paths. Add native build validation. | Clean macOS checkout → dependency resolution → Capacitor sync → Xcode archive succeeds. Source inspection alone is not an archive result. |
| 15 | P1 before release · advisory | **Resolve dependency advisories and exposed development defaults.** Apply compatible dependency updates, assess each remaining exception's reachable path, make LAN serving explicit, and add advisory monitoring. | Audit clean or reviewed scoped exceptions; build/lint/tests/native packaging pass; no unexpected externally listening test/dev server. |

## Order of work

1. **Career transaction foundation:** 01–07, 09–10 and 12. Establish one mutation/save/event owner, validated recovery and save-scoped idempotency. Write integration tests reproducing the existing failures before changing behavior.
2. **Complete the football loop:** 08, 11, 13, 16–25, 28 and 33. Route player actions through the same rules used by the simulation; prove outcomes survive weeks and reloads.
3. **Truthful management and progression:** 26–27, 29–32. Fix destinations, costs, redeemable rewards and supported settings; decide checkout/content-pack launch scope.
4. **Redesign in coherent screen families:** use the handoff below. Shared navigation, headers, cards, sheets and tokens first; then Home/Squad/Match; then Club/Market/World; then settings, onboarding and edge states.
5. **Release qualification:** 14–15 and 34–36. Dependency/native work may run alongside earlier steps; release waits for all applicable P1 gates and the real-device pass.

A milestone is complete when its player-visible result, saved state and next-week consequences agree. A screen rendering successfully is not enough.

### Shared visual improvements

- The current app relies heavily on similar dark rounded panels. Give match, roster, finance and editorial/social surfaces distinct layouts while retaining one type/spacing/color system.
- Reduce repeated explanatory blocks above the useful data. Keep context available through concise secondary text or expandable details.
- Audit small secondary labels and horizontally scrolling section rails. The screenshot checks do not prove text scaling, contrast or screen-reader quality.
- Review header space and scrolling behavior together. An empty compact header at the top of several mobile screens uses space that could carry navigation or a meaningful action.
- Preserve the five primary sections and define a consistent active state, back behavior and page title. Ensure content remains reachable above fixed controls after scrolling.
- Design loading, empty, error, busy, disabled, success and recovery states alongside the ideal populated screen. Desktop parity is part of the same design, not a later sidebar addition.
